## 學到 / 確認的東西

### 1. AI 生成的架構報告要拆開來檢驗

那份 Gemini 報告讀起來很流暢，每一章都自圓其說。但每個技術細節往下挖一層就空：演算法跳過了核心、API 用法寫錯（`isContainer` 已 deprecated、`PeriodicWork setInitialDelay` 只影響第一次觸發）、`createFromAsset` 用法前後矛盾、甚至有直接的 syntax error（`entities =,`）。

**啟示：AI 報告作為「靈感與結構參考」可以，但任何具體 API、任何能被編譯的東西、任何時間相關的排程邏輯，都要實際 build 過才能信。**

### 2. PeriodicWorkRequest 不能拿來做「準時推播」

`PeriodicWorkRequest` 的設計是「在這個週期內某個時間點觸發」，**不是準時觸發**。Google 文件明確寫了 flexInterval 預設是 interval 的 1/4，意思是設 24 小時實際可能在 18~24 小時的某個時間。

**正確做法：**
```kotlin
// 計算到明天 7:00 的延遲
val now = LocalDateTime.now()
val target = now.toLocalDate().plusDays(1).atTime(7, 0)
val delay = Duration.between(now, target).toMillis()

OneTimeWorkRequestBuilder<DailyFortuneWorker>()
    .setInitialDelay(delay, TimeUnit.MILLISECONDS)
    .build()
```

每次 Worker 執行完，自己再排明天的下一次。

### 3. 命盤資料表的破壞性重建是長者 App 的災難

`fallbackToDestructiveMigration()` 在開發階段很方便，但生產環境如果用在 family_members 上，**長者一升級就要重輸所有家人的農曆生日**。長者通常不會重輸第二次，App 直接被棄用。

**正確做法：**
- 字典表（唯讀、可重建）→ 可用 destructive
- 家人表（使用者輸入）→ 必走真 migration
- Room 支援不同表用不同策略，但需要分庫或在 callback 裡手動處理

## 遇到的問題（解了 + 記下）

### 1. `gradle.properties` 的 JVM 設定 key 名稱寫錯

`org.gradle.jvm.args` 是錯的（多了個點），正確是 `org.gradle.jvmargs`。daemon 在 thrashing 時拋的訊息有誤導，看起來像是 daemon 有讀到設定但 heap 不夠，實際上根本沒讀到。

解法：改 key 後正常。

### 2. Unit Test CLI 跑不起來（未解，繞過）

```
LunarCalendarTest > initializationError FAILED
java.lang.ClassNotFoundException
```

經 `--info` 追查，是因為：
- Gradle 8.11 的 test worker 用 `@argfile` 傳 classpath
- argfile 是 UTF-8 編寫但 Java 17 預設用 native encoding（Windows 是 GBK）解析
- 專案路徑含中文 `今日紫微`，被 GBK 解碼成亂碼，找不到目錄
- `.class` 檔本身正確編譯在 `build/tmp/kotlin-classes/debugUnitTest/`，問題只在 classpath 解析

**已試但無效的解法：**
- `gradle.properties` 加 `systemProp.file.encoding=UTF-8` + `systemProp.sun.jnu.encoding=UTF-8`
- `testOptions.unitTests.all { jvmArgs(...) }`

**推測有效但暫不嘗試的解法：**
- 升級到 Java 21（21+ argfile 預設 UTF-8）— 動使用者環境
- 把專案搬到無中文路徑 — 動專案結構，違反使用者習慣
- 在 build.gradle 自訂 task 直接傳 classpath 不用 argfile

**目前的繞道：**
