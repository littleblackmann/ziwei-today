## 遇到的問題

### 1. SettingsViewModel 用 combine 太多 flow 一開始寫得繞
最初試圖用兩層 combine + state.let { } 包成 StateFlow，編譯不過。改成「一個 MutableStateFlow + 多個 viewModelScope.launch collect」更清楚直接。

### 2. HomeScreen 的 contentDescription / semantics
寫了個 `private fun Modifier.semantics(...)` extension 想包，發現重複命名衝突。改用直接 `import androidx.compose.ui.semantics.{contentDescription, semantics}` 直接用標準 API。

### 3. SettingsScreen 多了 backupMessage 參數但沒人傳
中途想做 Snackbar 但跨層複雜，回退用 Toast（在 NavHost 那層處理）。

### 4. PushScheduler 需要 Context 但 ViewModel 不該持有
解法：把 ServiceLocator.appContext 從 private 改 public 暴露，ViewModel 直接從 ServiceLocator 拿 context 給 PushScheduler。

## 學到 / 確認的東西

### 1. SAF (Storage Access Framework) 是 Android 備份的唯一乾淨答案
備份匯出/匯入用 `ActivityResultContracts.CreateDocument` / `OpenDocument` 完全不需要 storage 權限，使用者自己選位置儲存。對長者 App 特別重要：跳過權限請求對話框。

### 2. WorkManager OneTimeWork 鏈式排程比 PeriodicWork 直觀
寫起來：「Worker.doWork() 跑完最後一行 PushScheduler.scheduleNext()」就好。不必煩惱 flexInterval、不必擔心系統優化把它延後。

### 3. Compose 無障礙寫法的最簡解：直接用標準 API
不要寫包裝 helper。`Modifier.semantics { contentDescription = ... }` 直接用即可。`isContainer` 在新版叫 `isTraversalGroup` 但本專案此版本沒用到，留待之後優化。

### 4. ServiceLocator 是「給沒有 DI 框架的 Android」最務實的選擇
我們現在有 4 個 ViewModel + 1 個 UseCase + 3 個 Repository + Worker + BackupManager 全部從 `ServiceLocator.xxx` 取得，沒有任何 Hilt / Koin 註解。新人接手只要看 `ServiceLocator.kt` 一個檔案就知道有什麼可用。

### 5. 流月精準計算這件事需要使用者真實命盤對照
今天我把流月從「過於簡化」改成「業界通用法則」並加文件，但真正驗證它正不正，得拿 3 組真實命盤對照才能說。**這是 V1.1 的工作**：找命理朋友幫忙對照流年/流月/流日宮位是否與「真正的紫微 App / 命理師」相符。
