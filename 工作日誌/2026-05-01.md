### 2. 命盤 CenterCard 重複渲染修復

**起點：** 使用者看到命盤中央出現兩個「命主資訊」區塊，佈局嚴重跑版。

**根因：** `TwelvePalaceGrid` 的迴圈邏輯：
```kotlin
// 舊代碼（有 bug）
row.forEach { branch ->
    if (branch == null) {
        if (rowIdx == 1 && row.indexOf(branch) == 1) { // ← 問題在這
            CenterCard(...)
        }
    }
}
```
`row.indexOf(null)` 永遠回傳 list 中**第一個** null 的 index（即 1）。Row 1 中有兩個 null（col 1 和 col 2），對兩個 null 都會進入 `rowIdx == 1 && row.indexOf(branch) == 1` 為 true 的分支，CenterCard 因此被渲染兩次。

額外問題：Row 2 和 Row 3 的 null 格子沒有渲染任何東西（連 Spacer 都沒有），導致這兩行只有 2 個元素參與 weight 分配，中間兩欄完全塌陷。

**討論收斂：** 改用 `forEachIndexed` 搭配 `colIdx` 精確比對格子位置，取代不可靠的 `indexOf`。Row 2 中心兩欄補 `Spacer(weight=2f)` 維持佈局比例，讓整個 4×4 grid 正確對齊。

**實作：**

| 檔案 | 改動 |
|---|---|
| `ui/chart/ChartScreen.kt` | `TwelvePalaceGrid` 的迴圈從 `row.forEach` 改為 `row.forEachIndexed { colIdx, branch }`，用 `when` 條件精確分配：`(1,1)` 放 CenterCard weight(2f)、`(1,2)` 跳過、`(2,1)` 放 Spacer weight(2f)、`(2,2)` 跳過、其餘 null 一律 Spacer weight(1f) |

修復後佈局：
```
Row 0: 巳(1f) 午(1f) 未(1f) 申(1f)          ← 4 宮各 weight 1f
Row 1: 辰(1f) [CenterCard 2f]    酉(1f)      ← weight 合計 4f ✓
Row 2: 卯(1f) [Spacer 2f]        戌(1f)      ← weight 合計 4f ✓
Row 3: 寅(1f) 丑(1f) 子(1f) 亥(1f)          ← 4 宮各 weight 1f
```

**驗證：** `assembleDebug` 通過，中央命主資訊只渲染一次，佈局比例正確。

## 討論但「先不做」的東西

### 命盤中央跨兩列視覺效果
- 為什麼想做：傳統紫微盤的中央是一個大方格，視覺上跨 Row 1 和 Row 2
- 為什麼先不做：Compose Row/Column 不支援跨列，需要 `Box` 絕對定位或 `Layout` 自訂測量，成本高、風險大
- 目前做法：Row 1 放 CenterCard、Row 2 放透明 Spacer，功能完整，只是視覺上是兩段而非一整塊
- 之後做的話：可以改用 `Canvas` 或 `Layout` 自訂繪製整個 4×4 命盤

### 既有快取自動重新生成
- 為什麼想做：用戶今天查過的記錄快取是 120-220 字的舊版，不會自動換成 300-500 字的新版
- 為什麼先不做：強制重刷快取會造成非預期的 API 消耗，使用者自己選擇「重新產生」即可
- 之後做的話：可以在快取裡加 `prompt_version` 欄位，版本不符時才自動失效

### 運勢結果做「展開 / 收合」兩層模式
- 為什麼想做：現在詳細解讀已經比一開始完整，但若後續再加長，部分使用者可能只想先看一句摘要和重點
- 為什麼先不做：目前先確認「較長內容 + 分段閱讀」是否已足夠；若體感 OK，就不一定需要再加互動複雜度
- 之後做的話：可以讓詳細解讀預設顯示前一段，點「展開完整解讀」再開第二、三段

### 主題別語氣差異化
- 為什麼想做：整體運勢、財運、感情、事業目前仍是同一套大語氣，只是內容依主題變動
- 為什麼先不做：先確認新版頁面與長文結構是否得到使用者認可，再決定要不要針對各主題再精修 prompt
- 之後做的話：可為財運偏務實、感情偏細膩、事業偏行動建議，讓主題辨識度更高

## 學到 / 確認的東西

### 1. `list.indexOf(null)` 在有多個 null 的 list 裡永遠只回傳第一個

`indexOf` 找到第一個符合條件的 index 就停止，所以 `listOf(A, null, null, B).indexOf(null)` 永遠是 `1`，不是 `2`。在迴圈裡要靠 index 判斷格子位置，**必須用 `forEachIndexed` 拿 `colIdx`**，不能事後再查。

### 2. Material 3 的 `LocalContentColor` 只在 `Surface` composable 內自動切換

`Box(modifier = Modifier.background(colorScheme.surface))` **不等於** `Surface(color = colorScheme.surface)`。前者只改背景顏色，`LocalContentColor` 不變；後者會同時把 `LocalContentColor` 切到對應的 `onSurface`。如果用 `Box` 當容器，內部 Text 必須明確指定 `color`，不能依賴隱式繼承。

### 3. OpenAI json_schema 的 description 欄位會影響輸出長度

在 json_schema properties 的 `description` 裡明確寫字數範圍（如「300-500 字」），搭配 `system instructions` 裡的細項要求，模型輸出長度和品質會顯著提升。單靠 system instructions 而 schema description 不配合，效果打折。

### 4. 日期選擇器這種高互動元件，穩定比「自訂感」更重要

今天原本一度想繼續修自訂 `WheelPicker`，但實際上它同時牽涉定位、字級、snap、中心判斷、農曆規則，越修越容易變成「局部好了，整體還是怪」。最後換成原生 `NumberPicker` 後，互動穩定度立刻高很多。這次再次確認：**輸入元件若已反覆出現視覺 / 手感問題，直接換穩定方案通常比硬修更省時間。**

### 5. 內容變完整，不等於單純把字數拉長

使用者真正感受到的「有沒有料」，常常來自內容是否有層次，而不是絕對字數。這次把結果頁改成「一句看懂 → 重點提醒 → 詳細解讀 → 命理依據」後，即使文字只是中幅增加，體感完整度也明顯上升。
